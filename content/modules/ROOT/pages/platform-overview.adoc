== Key takeaway

*9 out of 11 services come directly from Red Hat.* +
*7 of those are installed through OLM — the Red Hat operator framework built into every OpenShift cluster.*

This is not a coincidence.
OpenShift is not just a Kubernetes distribution: it ships with a curated ecosystem of certified operators.
When you subscribed to OpenShift, you already had access to GitOps, Pipelines, Dev Spaces, Keycloak, and External Secrets — without additional procurement.

The remaining Red Hat products extend the base platform through two additional bundles:

* **Red Hat Quay** is available as a standalone subscription or as part of OpenShift Platform Plus.
* **Red Hat Trusted Artifact Signer** and **Red Hat Developer Hub** are part of the **Red Hat Advanced Developer Suite** — Red Hat's bundle focused on developer productivity, supply chain security, and the internal developer portal experience.

[NOTE]
====
*Two components are not Red Hat products:*

* **HashiCorp Vault** is used here as the secrets backend. In a production environment it may be replaced by a managed secrets service (AWS Secrets Manager, Azure Key Vault, etc.) or Red Hat's own secrets management integrations — the External Secrets Operator supports them all through the same `ClusterSecretStore` abstraction.
* **GitLab** provides source control and mirrors the Helm chart repository. In a real deployment, any Git provider (GitHub, Gitea, Bitbucket) works equally well with ArgoCD and OpenShift Pipelines.
====

== The operator pattern

Every Red Hat component in this lab was installed the same way: an OLM `Subscription` tells the cluster which operator to install, and a Custom Resource (CR) tells the operator what to run.

[source]
----
Subscription  →  installs the operator
      ↓
Custom Resource  →  describes the desired state
      ↓
Operator  →  reconciles continuously toward that state
----

This pattern means that:

* *Day-2 operations are declarative*: update a CR and the operator handles the rollout, migration, or reconfiguration.
* *GitOps is natural*: CRs are YAML files committed to Git and applied by ArgoCD — the same workflow as any other Kubernetes resource.
* *Upgrades are automated*: OLM watches the catalog and can apply operator updates without manual intervention.

== The role of ArgoCD

Every component in this lab — operator subscriptions, CRs, Helm charts — is deployed through an ArgoCD `Application`.
ArgoCD is the single enforcement point: Git is the source of truth, and ArgoCD continuously reconciles the cluster toward it.

This means the entire platform is:

* **Reproducible**: delete the cluster, re-run Ansible, get back an identical environment
* **Auditable**: every change is a Git commit
* **Self-healing**: ArgoCD detects and corrects manual drift automatically
