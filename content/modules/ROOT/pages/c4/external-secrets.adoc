== What External Secrets Operator provides

External Secrets Operator bridges external secret management systems (such as HashiCorp Vault) into Kubernetes. It:

* Syncs secrets from Vault into Kubernetes `Secret` resources
* Keeps secrets up to date when they change in the external store
* Avoids storing sensitive data in Git
* Uses `ExternalSecret` and `ClusterSecretStore` CRDs to define the sync behavior

== The Helm Chart

The ArgoCD Application points to the `external-secrets` chart in your GitLab repository.
Browse it here: {helm_repo_browse}/-/tree/{helm_repo_tag}/external-secrets[{helm_repo_browse}/-/tree/{helm_repo_tag}/external-secrets^]

The chart deploys the **Red Hat External Secrets Operator** via OLM and configures a `ClusterSecretStore` pointing to Vault. It contains three resources deployed in sequence using ArgoCD sync waves:

[cols="1,2,1",options="header"]
|===
|Resource |What it does |Sync wave

|`Namespace`
|Creates the `external-secrets-operator` namespace
|0

|`OperatorGroup`
|Scopes OLM to the operator namespace
|0

|`Subscription`
|Installs the operator from the `redhat-operators` catalog
|1

|`ClusterSecretStore`
|Connects to Vault once the operator CRDs are available
|2
|===


== Create the ArgoCD Application

Create the ArgoCD Application YAML that deploys External Secrets Operator and its Vault integration:

[source,bash,subs="attributes"]
----
cat <<'EOF' > external-secrets-application.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: external-secrets
  namespace: openshift-gitops
  finalizers:
    - resources-finalizer.argocd.argoproj.io/foreground
spec:
  destination:
    server: https://kubernetes.default.svc
    namespace: external-secrets-operator
  project: default
  source:
    repoURL: {helm_repo}
    targetRevision: {helm_repo_tag}
    path: external-secrets
    helm:
      values: |
        vault-integration:
          vault:
            namespace: vault
            name: vault
            auth:
              namespace: default
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    retry:
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m0s
      limit: 2
    syncOptions:
      - CreateNamespace=true
EOF
----

== ClusterSecretStore and Vault

The Helm chart deploys a `ClusterSecretStore` named `vault-secret-store` that connects to the Vault instance in the `vault` namespace. This store allows `ExternalSecret` resources in any namespace to pull secrets from Vault using the configured authentication (Kubernetes auth with `rhdh-role`).

=== Check the ClusterSecretStore status

[source,bash,subs="attributes"]
----
oc get clustersecretstore vault-secret-store \
  -o jsonpath='Ready={.status.conditions[?(@.type=="Ready")].status}{"\n"}Message={.status.conditions[?(@.type=="Ready")].message}{"\n"}'
----

You should see `Ready=True`. If not, confirm the ESO pods are running:

[source,bash,subs="attributes"]
----
oc get pods -n external-secrets
----

== Test: End-to-End Secret Sync from Vault

This test validates the full pipeline: write a secret in Vault → ESO syncs it → verify the resulting Kubernetes `Secret`.

=== Step 1 — Write a test secret in Vault

[source,bash,subs="attributes"]
----
VAULT_TOKEN=$(oc get secret vault-token -n vault -o jsonpath='{.data.token}' | base64 -d)

oc exec -n vault vault-0 -- \
  env VAULT_TOKEN=$VAULT_TOKEN \
  vault kv put kv/test/hello username="platform-engineer" password="s3cr3t!"
----

=== Step 2 — Create an ExternalSecret

[source,bash,subs="attributes"]
----
cat <<'EOF' | oc apply -f -
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: vault-test-secret
  namespace: default
spec:
  refreshInterval: 1m
  secretStoreRef:
    name: vault-secret-store
    kind: ClusterSecretStore
  target:
    name: vault-test-secret
    creationPolicy: Owner
  data:
    - secretKey: username
      remoteRef:
        key: kv/data/test/hello
        property: username
    - secretKey: password
      remoteRef:
        key: kv/data/test/hello
        property: password
EOF
----

=== Step 3 — Verify the sync

Wait a few seconds, then check that the `ExternalSecret` is in `SecretSynced` state:

[source,bash,subs="attributes"]
----
oc get externalsecret vault-test-secret -n default \
  -o jsonpath='Status={.status.conditions[?(@.type=="Ready")].reason}{"\n"}'
----

Expected output: `Status=SecretSynced`

Then verify the Kubernetes `Secret` was created with the correct values:

[source,bash,subs="attributes"]
----
oc get secret vault-test-secret -n default \
  -o jsonpath='username={.data.username}{"\n"}' | \
  awk -F= '{print $1"="} NR==1{cmd="echo "$2" | base64 -d"; cmd | getline v; close(cmd); print v}'

# Or simply decode both fields:
echo "username: $(oc get secret vault-test-secret -n default -o jsonpath='{.data.username}' | base64 -d)"
echo "password: $(oc get secret vault-test-secret -n default -o jsonpath='{.data.password}' | base64 -d)"
----

Expected:
----
username: platform-engineer
password: s3cr3t!
----

=== Step 4 — Clean up the test resources

[source,bash,subs="attributes"]
----
oc delete externalsecret vault-test-secret -n default
oc delete secret vault-test-secret -n default 2>/dev/null || true

VAULT_TOKEN=$(oc get secret vault-token -n vault -o jsonpath='{.data.token}' | base64 -d)
oc exec -n vault vault-0 -- \
  env VAULT_TOKEN=$VAULT_TOKEN \
  vault kv delete kv/test/hello
----
