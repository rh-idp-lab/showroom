== Why Red Hat products, not DIY?

Building an IDP is deceptively simple on paper: pick open-source tools, wire them together, and ship. In practice, "DIY" becomes a full-time platform maintenance burden. Here is why choosing an integrated Red Hat stack changes the outcome.

=== Standardization instead of sprawl

A DIY platform usually starts with one team's preferences and forks every time a new team joins. Each team ends up with its own Tekton configuration, its own ArgoCD instance, its own secrets approach. Onboarding a new developer means learning N platforms instead of one.

Red Hat Developer Hub enforces golden paths. Templates are the contract: every team starts from the same baseline. The catalog makes every service discoverable. There is exactly one way to create a project at Golden Path Inc., and it takes one click.

=== Security by default, not as an afterthought

DIY security means manually integrating Sigstore, configuring OPA policies, enabling image scanning, and keeping everything up to date when CVEs land. The integration gaps between tools you assembled yourself are where vulnerabilities hide.

With the Red Hat stack, Red Hat Trusted Artifact Signer ships as an operator. Red Hat Quay integrates image scanning natively. RHBK handles OAuth2/OIDC for every service with no custom code. External Secrets Operator removes secrets from source code entirely. Each component ships with security hardening built in.

=== Enterprise support when it matters

Open-source tools come with community support. If your pipeline breaks at 2 AM before a critical release, the Tekton Slack channel may or may not have an answer by morning.

Every component you deployed today is covered by Red Hat subscriptions and backed by Red Hat's support SLAs. Security patches, CVE advisories, and compatibility guarantees across OpenShift releases come with the subscription. You are not alone.

The total cost of ownership of a DIY platform is not the cost of open-source licenses. It is the cost of the engineers who maintain the glue, the outages caused by incompatible upgrades, and the developers slowed down by inconsistent tools.

== What comes next

This platform is a foundation, not a ceiling. Possible next steps:

* *AI workloads*: A modern IDP must be able to host AI workloads and make them consumable by developers with no ML expertise. Red Hat OpenShift AI provides a managed environment for training, serving, and monitoring models directly on the cluster. Expose model endpoints through RHDH software templates so developers access AI capabilities the same way they access any other service — from the catalog, in one click.
* *More golden paths*: Add templates for Quarkus, Spring Boot, Python, or Node.js microservices.
* *Observability*: Integrate OpenShift Monitoring and Grafana dashboards into the RHDH catalog.
* *Service mesh*: Add Red Hat OpenShift Service Mesh for traffic management, mTLS, and tracing.
* *Custom plugins*: Surface your organization's internal tools (ITSM, cost management, compliance) directly in RHDH.
* *Multi-cluster*: Extend the platform to manage staging and production clusters from the same GitOps root.

== Platform Engineering Principles: mission accomplished

At the start of this lab, Module 1 introduced six principles from link:https://platformengineering.org[platformengineering.org^]. Here is how each one was implemented.

[cols="2,2,3",options="header"]
|===
|Principle |Where you applied it |How

|*Product Mindset*
|Module 6: Developer Hub
|RHDH is the front door of the platform. It is designed around developer needs: one login, one catalog, one place for services, pipelines, and templates.

|*Golden Paths, Not Golden Cages*
|Module 6: Software Templates
|Every template bundles Git, Tekton, ArgoCD, Quay, and Vault configuration into a single form. The right way is the easy way — teams are not forced into it, but they have no reason to bypass it.

|*Self-Service via Abstraction*
|Module 9: Developer Experience
|A developer created a production-ready application without a ticket, a runbook, or any help from the platform team. One form, one click, done.

|*Developer Experience (DevEx)*
|Module 4: Dev Spaces
|Zero local setup. New developers are productive from a browser tab on day one, with a standardized environment identical to every other developer on the team.

|*Shared Responsibility & Governance*
|Module 4: External Secrets + Module 7: Trusted Artifact Signer
|Secrets never touch Git. Every image is cryptographically signed at build time. Security and compliance are enforced by the platform, not by individual discipline.

|*GitOps as the rule*
|Every module
|Every deployment in this lab — platform components, pipelines, application environments — was created via an ArgoCD `Application` pointing to a Helm chart in Git. No exceptions.
|===
