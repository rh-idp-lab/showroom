= Deploy a Dedicated ArgoCD Instance
:navtitle: Deploy a Dedicated ArgoCD Instance

[NOTE]
====
*Challenge #5: "Each team deploys differently. No visibility, no consistency, no rollback."*

Golden Path Inc.'s dev teams use a mix of `kubectl apply`, shell scripts, and "just SSH into the server". Deployments are invisible, inconsistent, and scary. You'll give developers their own GitOps instance: a dedicated ArgoCD that handles application deployments, separate from the platform ArgoCD you've been using.
====

== Why a separate ArgoCD instance

The cluster GitOps ArgoCD (in `openshift-gitops`) manages platform components. A separate ArgoCD instance in `rhdh-gitops` is used for developer applications. This separation provides:

* Clear boundary: platform team owns cluster GitOps; developers use app GitOps
* Different RBAC and access control per instance
* Isolation so developer deployments do not affect platform stability

== The Helm Chart

The ArgoCD Application points to the `gitops` chart in your GitLab repository.
Browse it here: {helm_repo_browse}/-/tree/{helm_repo_tag}/gitops[{helm_repo_browse}/-/tree/{helm_repo_tag}/gitops^]

The chart deploys a dedicated ArgoCD instance (`ArgoCD` CR) with its RBAC, routes, and resource customizations pre-configured.

== Create the ArgoCD Application

Create the ArgoCD Application YAML that deploys the dedicated ArgoCD instance:

[source,bash,subs="attributes"]
----
cat <<'EOF' > rhdh-gitops-application.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: rhdh-gitops
  namespace: openshift-gitops
  finalizers:
    - resources-finalizer.argocd.argoproj.io/foreground
spec:
  destination:
    server: https://kubernetes.default.svc
    namespace: rhdh-gitops
  project: default
  source:
    repoURL: {helm_repo}
    targetRevision: {helm_repo_tag}
    path: gitops
    helm:
      values: |
        nameOverride: rhdh-gitops
        password: {common_password}
        controller:
          resources:
            requests:
              cpu: 500m
              memory: 1Gi
            limits:
              cpu: 1500m
              memory: 3Gi
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    retry:
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m0s
      limit: 2
    syncOptions:
      - CreateNamespace=true
      - RespectIgnoreDifferences=true
EOF
----

== Apply the Application

[source,bash,subs="attributes"]
----
oc apply -f rhdh-gitops-application.yaml
----

== Verify in ArgoCD UI

Open the ArgoCD UI and confirm the `rhdh-gitops` application syncs successfully and shows **Healthy** status.

ArgoCD link: https://openshift-gitops-server-openshift-gitops.{openshift_cluster_ingress_domain}/applications/rhdh-gitops[RHDH GitOps Application in ArgoCD^]

== Verify in the OpenShift Console

. Open the https://console-openshift-console.{openshift_cluster_ingress_domain}[OpenShift Console^]
. Navigate to the *Topology* view in the `rhdh-gitops` project
. Verify the ArgoCD server, repo-server, and application-controller pods are `Running`

Direct link: https://console-openshift-console.{openshift_cluster_ingress_domain}/topology/ns/rhdh-gitops?view=graph[Topology (rhdh-gitops)^]

NOTE: This component does not install an operator: it deploys ArgoCD resources directly via the Helm chart.

== Verify with CLI

[source,bash,subs="attributes"]
----
oc get pods -n rhdh-gitops -w
----

TIP: The `-w` flag watches for changes in real-time. Press **Ctrl+C** to stop watching once all pods show `Running` and `1/1` or `2/2` READY.

== Access the new ArgoCD

Once deployed, the dedicated ArgoCD UI is available at:

link:https://rhdh-gitops-server-rhdh-gitops.{openshift_cluster_ingress_domain}[RHDH GitOps^]

Click **LOG IN VIA OPENSHIFT** and log in with `user1` / `{common_password}`.
