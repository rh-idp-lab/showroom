== Why OpenShift Pipelines?

For CI/CD pipelines in this IDP, we chose **OpenShift Pipelines** (based on Tekton) rather than GitLab CI. Both are valid options — GitLab CI is already available in this cluster and perfectly capable of running pipelines. However, OpenShift Pipelines offers a compelling advantage for a platform engineering context:

* **Native to OpenShift** — it ships as a certified operator in the Red Hat catalog; no additional infrastructure to manage
* **Kubernetes-native execution** — each pipeline step runs as an isolated container pod, with full resource control and auditability
* **Declarative pipeline-as-code** — Tasks, Pipelines, and PipelineRuns are standard Kubernetes resources stored in Git
* **Deep OpenShift integration** — built-in triggers, cluster-level RBAC, and integration with image streams and the OpenShift Console
* **Separation of concerns** — GitLab manages source code and merge requests; OpenShift Pipelines handles the build and deployment orchestration

In a real-world IDP, you would likely use both: GitLab CI for lightweight repository-level automation (linting, unit tests) and OpenShift Pipelines for cluster-side build, security scan, and deployment workflows.

== What OpenShift Pipelines provides

* Native Kubernetes pipelines that run as containers
* A declarative pipeline-as-code model using YAML
* Built-in integrations with Git, container registries, and OpenShift
* Standard CI/CD workflows: build, test, deploy
* Tekton resources: Tasks, Pipelines, PipelineRuns, and Triggers

== The Helm Chart

The ArgoCD Application points to the `openshift-pipelines` chart in your GitLab repository.
Browse it here: {helm_repo_browse}/-/tree/{helm_repo_tag}/openshift-pipelines[{helm_repo_browse}/-/tree/{helm_repo_tag}/openshift-pipelines^]

The chart contains a single `Subscription` resource that instructs OLM (Operator Lifecycle Manager) to install the OpenShift Pipelines operator from the Red Hat catalog. ArgoCD deploys this resource; OLM takes care of the rest — downloading, installing, and keeping the operator up to date.

== Create the ArgoCD Application

Create the ArgoCD Application YAML that deploys the OpenShift Pipelines Operator from the Helm chart:

[source,bash,subs="attributes"]
----
cat <<'EOF' > pipelines-application.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: openshift-pipelines
  namespace: openshift-gitops
  finalizers:
    - resources-finalizer.argocd.argoproj.io/foreground
spec:
  destination:
    server: https://kubernetes.default.svc
    namespace: openshift-operators
  project: default
  source:
    repoURL: {helm_repo}
    targetRevision: {helm_repo_tag}
    path: openshift-pipelines
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    retry:
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m0s
      limit: 2
    syncOptions:
      - CreateNamespace=false
      - RespectIgnoreDifferences=true
EOF
----

== Apply the Application

[source,bash,subs="attributes"]
----
oc apply -f pipelines-application.yaml
----

== Verify in ArgoCD UI

Open the https://openshift-gitops-server-openshift-gitops.{openshift_cluster_ingress_domain}[ArgoCD UI^] and confirm the `openshift-pipelines` application syncs successfully and shows a **Healthy** status.

== Verify in the OpenShift Console

. Open the https://console-openshift-console.{openshift_cluster_ingress_domain}[OpenShift Console^]
. Navigate to *Operators → Installed Operators*
. Select the `openshift-operators` project from the dropdown
. Confirm **Red Hat OpenShift Pipelines** appears with status `Succeeded`

Direct link: https://console-openshift-console.{openshift_cluster_ingress_domain}/k8s/ns/openshift-operators/operators.coreos.com~v1alpha1~ClusterServiceVersion[Installed Operators (openshift-operators)^]

Then explore the deployed workloads:

. In the Console, navigate to *Workloads → Pods*
. Switch to the `openshift-pipelines` project from the dropdown
. You should see the Pipelines controller, webhook, and trigger components with `Running` status

Direct link: https://console-openshift-console.{openshift_cluster_ingress_domain}/k8s/ns/openshift-pipelines/core~v1~Pod[Pods (openshift-pipelines)^]

== Verify with CLI

[source,bash,subs="attributes"]
----
oc get pods -n openshift-pipelines -w
----

TIP: The `-w` flag watches for changes in real-time. Press **Ctrl+C** to stop watching.

Expect pipeline controller pods to show `Running` status and `1/1` or `2/2` READY.

Then verify the TektonConfig:

[source,bash,subs="attributes"]
----
oc get tektonconfig -w
----

Press **Ctrl+C** once the TektonConfig shows `Ready=True`.

TIP: 🎉 **First component deployed!** You just witnessed the GitOps pattern in action: ArgoCD Application → Helm chart → reconciled resources. Every subsequent deployment follows this same pattern. This is the foundation of your IDP — version-controlled infrastructure as code.

TIP: 💡 **Platform health check** — You can check all platform components at any time:
+
[source,bash,subs="attributes"]
----
for ns in openshift-gitops gitlab vault openshift-storage sso openshift-pipelines quay-registry external-secrets rhdh-gitops openshift-devspaces trusted-artifact-signer rhdh; do
  echo -n "$(echo $ns | awk '{print toupper(substr($0,1,1)) substr($0,2)}' | sed 's/-/ /g'): "
  oc get pods -n $ns --no-headers 2>/dev/null | awk '{if ($3=="Running" && $2~/\//){split($2,a,"/"); if(a[1]==a[2]) r++} t++} END {if(t>0) print r"/"t" ready"; else print "not deployed"}'
done
----
